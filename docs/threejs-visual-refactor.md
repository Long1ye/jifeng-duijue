## 1. 目标与范围

在现有中路对线玩法上，建立以 Three.js 为渲染基础、可模块化搭建和持续扩展的像素 ARPG 场景。用户偏好的美术参考为《Eldest Souls》和《Hunt the Night》，地图形成自己的材质与构图语言。

**本次交付是游戏画面的全面升级。** 更换渲染器并达到旧版画面只算技术迁移中间成果，不能作为最终完成条件。旧版基线用于核对玩法、操作、内容和性能变化；不要求新旧截图像素一致，也不把旧地图构图、素材质量或效果实现当作新版上限。

### 画面升级的交付标准

| 维度 | 新版需要交付的提升 | 验收方式 |
| --- | --- | --- |
| 地图构图与空间 | 重新组织建筑体量、道路边界、立面、前中远景；形成有厚度和纵深的场景 | 同类出生、交战与建筑场景对照，实际游戏尺寸检查层次与通行辨识 |
| tile 与材质 | 统一像素密度，重做必要的地表、转角、过渡和模块接口，减少机械重复与拼贴感 | 拼接样板、连续道路和全图区块边界验收 |
| 建筑与环境资产 | 以所选美术方向重新设计或升级主要建筑、岩壁、植被和装饰，统一轮廓与细节密度 | 资产同屏比例与场景整体风格验收；不以旧图直接贴入三维场景作为定稿 |
| 配色与光影 | 建立一致的冷暖、明暗和焦点层级，强化材质与接地，保持战斗信息清晰 | 明暗区域、不同阵营和环境开关对照；沿用不恢复技能照地光的约束 |
| 角色与战斗表现 | 改善脚底接地、受光融合、遮挡、特效空间关系和命中反馈；逐项评估旧动画及特效的保留、改造或替换 | 八向移动、绕塔、普攻与技能关键帧/动态验收，伤害和动作时序保持一致 |
| HUD 与整体协调 | 复核血条、选中、技能提示与界面在新环境中的配色、比例和可读性，必要时调整视觉样式 | 正常游戏窗口和密集交战场景验收，既有操作功能完整 |

现有二维角色动画可以作为首轮样板的比例锚点，最终复用取决于新版风格与实机质量。全面升级不要求无差别重画所有资源，但每类资产都要有质量判断与采用理由。P2 记录各维度的明确采用标准和用户反馈，P4/P5 逐项附证据验收；不能仅用测试通过、特效数量增加或模糊后处理宣布画面升级完成。

| 类别 | 当前约定 | 状态 |
| --- | --- | --- |
| 用户方向 | 使用 Three.js 重构画面；地图支持不同 tile；偏好上述两款作品 | 已确认方向 |
| 交付目标 | 全面提升画面质量；旧版等价仅为迁移中间节点 | 用户已明确 |
| 美术主次 | Eldest Souls 负责建筑体量与空间，Hunt the Night 负责材质、植被和环境细节 | 建议，待局部样板验收 |
| 技术路线 | Three.js固定视角2.5D：像素地表、分层建筑/桥体美术、必要三维结构、二维角色 | [目标实景落地方案](howling-abyss-art-implementation.md)，主相机与生产规格待小样校准 |
| 初期内容 | 优先用现有冰桥制作局部样板，再决定全图美术范围 | 建议，P0 明确 |
| 平台 | 沿用桌面浏览器与键鼠操作 | 当前基线 |

本次不自动增加联网、多英雄、自由旋转镜头、三维角色重制或 ARPG 刷宝玩法。视觉高度先用于表现；跳跃平台、跨层战斗和新增地形阻挡属于单独玩法变更。

沿用已有约束：技能与投射物不恢复动态照地光；保留适量环境照明；环境效果不得掩盖技能、单位和血条。改变这些约束时先记录明确的用户决定。

## 2. 基线与文档职责

## 3. 架构边界与迁移方式

采用并行开发入口，保留 Phaser 作为对照和回退路径。P1 已用独立 `/three.html?map=howling` 页面隔离灰盒，默认 `/` 继续使用 Phaser，当前不提供 renderer 查询参数。每页只实例化自己的渲染器，切换通过导航重载完成。普通构建包含实验页，分享构建暂保留旧默认入口。

以下是建议目录，落实时按实际职责调整；不预先创建空框架，也不批量移动旧文件。

```text
src/game/                 比赛状态、固定步模拟、规则和战斗事件
src/presentation/         与引擎无关的动画时序、视图快照和表现计算
src/render/               迁移期间保留现有 Phaser 实现
src/render-three/         场景、相机、地图、角色、特效和资源释放
src/maps/                 地图实例、tile 定义、地图版本及加载校验
src/ui/                   DOM HUD 与音频
```

依赖方向为：启动层连接模拟、输入适配、渲染和 UI；表现层读取模拟状态与事件；模拟不引用渲染器、贴图或 DOM。不要让 Three.js 场景接管伤害判定。

迁移时建立最小宿主接口：启动、每帧更新、窗口调整、暂停状态同步、释放，以及 HUD 真正需要的查询和命令。先盘点 `main.ts` 对 `ArenaScene` 属性的直接访问，再逐项适配，避免把现有大型场景的所有字段复制进接口。

- 模拟仍以固定 60 Hz 更新；插值仅影响呈现，不改命中时间和移动距离。
- 输入先统一为逻辑世界命令，再提交模拟；渲染器只负责拾取与坐标转换。
- 战斗事件在同一帧由宿主统一取出，再分发给动画、音频和反馈；不能由多个消费者分别清空同一事件队列。
- 动画读取比赛时间；暂停冻结，重开复位。不得另开独立定时器驱动技能播放。
- 纹理、材质、几何体、渲染目标、事件监听和对象池都有明确释放方；缓存共享资源采用引用计数或统一生命周期。

### 坐标契约

P1 必须定义三种坐标：模拟平面 `(x,y)`、Three.js 世界 `(X,Y,Z)`、屏幕像素。地面使用 `X/Z`，`Y` 表示视觉高度；角色逻辑位置由脚底锚点映射到地面。

默认保留现有模拟距离度量，先建立可逆的平面映射。若为了改变桥的视觉比例引入非等比变换，必须同步验证攻击范围、速度观感与拾取；不能只拉伸地图。若决定将模拟改为未投影的地面坐标，应单独立项迁移距离、碰撞、路点和测试，不能隐含在美术任务中。

鼠标射线先与逻辑地面或指定可行走面求交，再逆映射回模拟平面。装饰模型不能抢走地面指令。八向角色朝向按投影后的屏幕运动方向选择；镜头角度变化需要重新检查方向对应关系。技能范围由逻辑几何投影，不能为了看起来圆而改变实际命中区域。

## 4. 地图与素材契约

地图分为地表、立体边界和独立装饰三层。tile 的逻辑占地与贴图画布大小分别记录，允许跨格建筑和自由摆放装饰。静态地表按区块合批或实例化；不要默认每个 tile 使用一个独立材质和绘制调用。

| 数据 | 必填信息 |
| --- | --- |
| tile 定义 | 稳定 ID、版本、类型、占地、连接规则、变体、材质引用、锚点、旋转限制 |
| 地图实例 | schemaVersion、地图 ID、网格原点、格子世界尺寸、区块、实例位置、变体种子 |
| 通行与碰撞 | 地表类型、可通行性、碰撞轮廓、可走高度；装饰默认不阻挡 |
| 游戏语义 | 出生点、塔位、兵线路点、基地等独立标记，不从贴图颜色或模型名称推断 |
| 角色与特效 | 图集、帧矩形、方向、时长、脚底锚点、挂点、表现高度与深度规则 |
| 素材清单 | 资源 ID、版本、来源、文件路径、尺寸、透明模式、色彩空间、采样策略、采用状态 |

迁移初期用适配器从现有 `Bridge` 数据构建地图，保留原通行行为。地图定义成为新唯一来源时，模拟、渲染和小地图一起切换；不能长期各维护一份不同的可走轮廓。新增障碍物先验收碰撞和兵线通路，再作为正式阻挡接入。

### 地表连接与立体模块

- 地表准备中心、边缘、内外角和必要的材质过渡；采用哪种邻接算法在 P1 记录。
- 相同材质用确定性变体减少重复；随机结果由地图种子复现，不随每次加载改变。
- 台阶、桥沿、墙体和悬崖统一高度级别、接缝位置和模块朝向；道路中央优先保证可读性。
- 已带透视的菱形图和手绘建筑不能直接充当普通三维表面纹理；标记为贴片资产或重新制作。
- 材质图集配置边缘扩展和 UV 留白，检查缩放后的串色、接缝及斜面闪烁。

### 美术规格冻结表

以下项目在局部样板中比较，验收后将最终值写入资源规格文档。表内候选值不是生产规格。

| 项目 | 起始候选 | 冻结条件 |
| --- | --- | --- |
| 基础 tile 贴图 | 32×32 或 64×64 | 与现有角色同屏比较，明确世界单位/纹素比例 |
| 模块尺寸 | 基础格及其整数倍占地 | 接缝、转角、跨格建筑和路宽全部成立 |
| 相机 | 固定倾角正交相机 | 八向移动、建筑高度和角色视角协调；记录角度、朝向、可见范围 |
| 渲染分辨率 | 按目标窗口比较多个内部尺寸 | 移动、缩放与窗口变化时像素清晰，性能达标 |
| 材质受光 | 地形受光，角色先用可控基础着色 | 角色不漂浮、不洗白，绘制阴影与环境光协调 |
| 调色 | 冷灰底色、少量暖色焦点 | 红蓝队伍及技能轮廓在明暗区域均可辨识 |

像素外观由素材、采样、内部渲染尺寸和相机共同决定。最近邻采样不能单独保证像素稳定；相机平移、斜面纹理缩小、不同 DPR 和浏览器缩放都要检查。角色画布大小不等于人物可见高度，比例以脚底到头顶的实际可见范围为准。

使用 `game-assets` 制作时，先确定资产契约与样板；涉及模板先发现模板并让用户选择，已有选择直接复用。保留源文件，采用版本写入清单；未检查尺寸、透明、接缝和实机比例的输出保持“候选”，不进入批量生产。

## 6. 验收方法

### 规则与交互

规则变化或宿主迁移时运行受影响测试；阶段合入和切换默认入口前运行 `npm test`、`npm run build`，涉及分享版本时运行 `npm run build:share`。只改文档不运行游戏测试，不把未执行检查写为通过。

新增自动化覆盖坐标往返、地面拾取、地图连接/通行一致性、事件单次消费、动画与比赛时间同步等关键边界，不为简单素材替换堆积实现镜像测试。

固定场景核对：出生与恢复、兵线交战、绕塔遮挡、八向移动、普攻与技能命中、控制与位移、三种胜负、暂停恢复、连续重开五次。用确定性输入比较迁移前后状态或事件序列；若现有模拟尚不支持确定性重放，先记录最小固定案例，不声称已经拥有回放系统。

### 画面

- 同一逻辑视野和同一场景保存 Phaser/Three.js 对照，记录相机、时间、窗口尺寸、DPR 和画质开关。
- 对照同时报告“功能是否保留”与“画面提升在哪里”；可以改变场景构图和资产设计，差异不能单凭像素差判为回归。每项升级写明具体变化、证据和未解决问题。
- 以实际游戏尺寸验收整体，再用整数最近邻放大检查像素；不能用模糊截图隐藏接缝。
- 检查角色脚底、塔前后遮挡、风墙透明边、旋风穿插、范围提示与真实命中位置。
- 覆盖默认/拉近视野、镜头平移、贴边、窗口调整与非整数浏览器缩放；记录可接受的降级行为。
- 原始二维角色先用接触阴影建立接地感；需要受光再单独试验材质，不假设贴上三维平面就自然融合。

### 性能与稳定性

桌面 60 FPS 为候选最低目标，120 FPS 为保留原项目高刷新体验的优化目标；P0 根据目标设备、分辨率和画质冻结验收档位。在此之前不能宣布已承诺所有设备 120 FPS。

同设备、同浏览器、同窗口与 DPR、同场景测量。出生区、中路交战、特效密集场景分别预热至少 10 秒、采样至少 60 秒；另做至少 10 分钟连续运行和五次重开。报告帧间隔中位数/P95、长帧、绘制调用、三角形数、纹理/几何体数量及可获得的 CPU/GPU 耗时；记录是否受显示器刷新率限制。

候选帧间隔 P95 门槛：60 FPS 档为 16.7 ms，120 FPS 档为 8.3 ms；正式门槛随设备与测量方法一起冻结。不能用单次 WebGL 提交时间替代实际呈现帧率，也不能直接复用旧报告中的受控耗时作为新版本成绩。

资源数量在重开和入口重载后应回到预期稳定范围；缓存保留须有解释，持续单调增长视为待修复问题。未达标先定位区块绘制、透明叠加、阴影和后处理成本，再降低非核心环境效果；不通过改动模拟频率换取表面帧率。

## 7. 日常执行与维护规则

每次工作开始先读本文件的“当前执行台账”，检查工作区改动和前置任务。结束时同步状态、证据、未解决问题和下一步。任何“已通过”必须有可访问的证据路径；“代码已接入”只对应“待验收”。

任务状态统一为：待开始、进行中、待验收、已通过、阻塞、暂缓。阻塞记录原因和解除条件；暂缓记录影响和重新启动条件。同一时间保持一个主要验收目标，独立任务可以并行推进。

每个任务使用以下简表，放在对应验证记录或 PR 中；本文件仅保留摘要链接，避免累积日志。

```markdown
任务 ID / 阶段：
目标与范围：
前置依赖：
变更文件或素材版本：
验收命令与人工场景：
结果与证据路径：
遗留问题：
回退方式：
下一步：
```

涉及坐标、素材契约、默认入口、渲染分辨率或地图数据格式的变更，更新决策记录。复杂决策另存 `docs/decisions/<ID>.md` 并从表中链接；简单决策直接保留在表内。被替代的决定保留历史并注明替代关系。

素材采用新版本路径和稳定资源 ID，不覆盖已采用源文件。更改地图 schema 时提供迁移或兼容加载，并验证旧地图。修复以最小任务提交，提交前检查 diff，避免把已有未提交改动带入无关任务。

### 回退与切换

P0 记录当前提交和未提交差异；已有用户修改不得通过 reset、清理目录或整体覆盖来移除。每阶段保留可恢复的代码/素材版本及入口说明。

Three.js 验收期间 Phaser 保持可启动；生产默认切换后遇到关键输入、战斗或性能回归，可按记录切回 Phaser 入口并回退默认选择。不得宣称只切 URL 就能回滚发布：发布回退还要恢复对应构建和素材版本。

P6 通过后先保留一个明确的对照验收周期，覆盖完整对局与发布构建，再单列清理任务移除 Phaser 依赖和旧场景。清理前确认没有 UI、音频或素材导入仍引用旧实现。
