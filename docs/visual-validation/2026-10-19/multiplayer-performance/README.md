# 联机移动卡顿与渲染开销优化

## 证据与原因

同机两个独立浏览器上下文，1280×800 窗口，各自控制英雄持续向中路移动，采样约 12 秒。初版 RTT 约 1 ms，但快照间隔的 95 分位为 69–73 ms。旧客户端在每次快照到达时重新启动固定 50 ms 插值，快照稍晚时先停住，再恢复移动；到包时位置与技能时钟也会重新对齐。

初版内部画面为 1920×1200，每帧重新计算并上传 512×288 的迷雾纹理；高刷新率下会产生多余的 CPU 与 GPU 工作。

## 修改

- 用 80 ms 快照历史与连续播放时钟替换按到包时间重启的插值；角色和投射物沿同一时刻插值，离散战斗状态和事件按对应快照推进。
- 到包不会倒退播放时钟；暂停／结束立即生效；闪现等大位移不跨墙插值；断流时停在已知状态，不推算伤害或继续移动。
- 后台积压的历史音效不在恢复页面时集中重放，历史有容量限制。
- 联机默认自动分辨率，初始宽 1280，持续低帧率才下降到 960／640，持续恢复后缓慢上调；可手动锁定原有画面精度。
- 迷雾视觉纹理最多 30 Hz 更新，TeamVision 可见性仍逐帧计算；迷雾动画时间保持连续。
- 房间信息未变化时跳过隐藏表单更新，进行中只更新状态条。增加 FPS 和快照等待提示。
- 服务端每次房间广播只序列化一次，复用同一内容发给双方。该服务端优化已在独立 5181 服务验证，现有 5180 服务未被重启。

## 本机前后对照

| 指标 | 之前：蓝／红 | 之后：蓝／红 |
| --- | --- | --- |
| 移动停住的采样帧 | 78 / 81 | 1 / 2 |
| 总采样帧 | 1700 / 1700 | 1882 / 1878 |
| 平均渲染耗时 | 3.49 / 3.48 ms | 2.47 / 2.48 ms |
| 95 分位帧间隔 | 9.9 / 9.8 ms | 6.2 / 6.2 ms |
| 平均帧率 | 145 / 145 | 159 / 159 |
| 内部画面 | 1920×1200 | 1280×800 |

原始报告见 `before.json` 和 `after.json`。这是一轮同机短测，包含少量 170–210 ms 的长帧；不能据此保证其他电脑的具体 FPS，也没有模拟公网高延迟。80 ms 缓冲用于改善平滑度，并未加入本地输入预测。

## 验证

- `npm test -- --maxWorkers=4`：165 个测试文件、908 项测试通过。
- `npm run check:server`、`npx tsc --noEmit`、`npm run build`：通过。
- `tests/network-smoothing.test.ts` 覆盖快照间隔抖动、逐帧位移与时间单调性、瞬移、断流、暂停恢复、事件去重、后台历史音效、自动分辨率阈值与恢复。
- `tests/three-war-fog.test.ts` 覆盖纹理更新节流与逐帧可见性检查相互独立。
- 独立 5181 服务运行 `scripts/validate-multiplayer.mjs`：双方移动／Q、同一权威状态、兵线、防御塔、Esc 不暂停和刷新重连均通过，页面运行时错误为零。
- `scripts/profile-multiplayer.mjs` 可复测两个客户端的帧时间、渲染耗时、快照间隔、传输量及移动停顿帧。

两台电脑刷新原有 5180 地址即可加载客户端优化；仍保留房间码和原有服务器战斗规则。
